# RelayPost：从真实首次使用出发的产品流程

日期：2026-11-03。依据用户对 `5e5b7b5` 候选的实际试用反馈。

## 已确认的问题与边界

用户不知道 Receive 如何发现文件，也不知道是否必须使用 U 盘。Send 中的
`UX Bob` 被误认为产品自动发现的对象；`connection` 暗示已经建立实时连接。
Home 重复分发任务，People 同时展示身份、安全码、公钥、连接卡、联系人与
本地存储，缺少明确的操作顺序。

之前的 Alice/Bob 预配资料只证明工程流程能够跑通。它跳过了用户真正需要
理解的首次身份设置、添加对方和文件搬运，不能作为普通用户易用性验收。
演示资料必须明确说明是模拟身份；不得将预置的测试收件人当成正常新用户起点。

反馈时的基线事实（`5e5b7b5`）：

- Prepare 在本机发件箱生成只供指定接收身份打开的保护包，不会发送网络数据。
- Export 将保护包复制到一个可访问目录。U 盘不是唯一载体，共享目录等也可以。
- Receive 仅在手选或拖入目录后查找包；进入页面没有自动扫描。
- 身份卡交换和完整安全码核验建立的是身份信任，不是实时网络连接。
- 本机准备给另一身份的发件不属于本机收件，必须在 Transfers 中查看后续动作。

用户已明确选择：**选择对方设备后直接发送，断网时再用文件包**。本轮边界为同一
局域网内发现和直传，不引入云中转、互联网 NAT 穿透、账号服务或远程执行。
已有加密包、接收校验和签名回执成为两种交付方式共用的基础设施，不另做一套
加密或“已送达”判断。

## 跨传输方式都成立的收敛

删除 Home。默认入口是 Send，导航收敛为 Send、Receive、Transfers 和收件对象
管理。Home 的复制、回执与恢复能力迁入已有 Transfers 路径，不保留旧 Home
兼容页。Transfers 应直接选中需要处理的记录。

界面必须分别回答两件事：

1. **谁能打开文件**：对方电脑的身份、名称及核验状态。
2. **文件怎样到达对方**：真实可用的交付方式及下一步操作。

尚未实现的交付方式不作为可选操作显示。

正常主流程是附近设备发现、身份核验、直接发送。离线身份卡交换明确标为
Add using identity card；文件包是用户主动选择的断网交付方式，不是静默尝试
其他路径的回退机制。

## 添加对方是一条完整任务

收件对象列表只有一个主入口 Add recipient，列表用紧凑行表示对象与核验状态。
自己的身份、公钥、本地路径与 CLI 说明移到 This computer 的独立详情面板。

正常添加流程展示附近设备，并自动交换公开身份卡；广播名称和网络地址都不等于
可信身份。两边仍须核对完整安全码，各自在本机明确确认。界面不得把“本机已核验”
误写成“对方也已核验”或“对方在线”。

离线身份卡路径按顺序说明分享本机身份卡、打开对方身份卡、核对完整安全码。
每一步只突出一个主动作；核验完成后，技术详情收回到次级面板。完整安全码和
双向信任检查保持不变。

Send 的收件人区域始终提供 Add recipient。核验成功时必须明确选择刚添加的
对象，再返回原任务，不能静默保留之前选中的其他收件人。

## 收件与交付状态必须可解释

Receive 只展示发给当前身份的可接收候选。自己的发件展示在 Transfers；空状态
必须说明从哪里取得文件，以及为什么本机 Prepare 后不会在这里成为收件。

候选发现、身份认证、解锁保存是不同阶段。自动发现不得绕过发送方签名、接收方
匹配、修复预算、密码解锁或保存校验，也不得自动解密或自动保存。

Prepared、已复制、接收方已保存、回执已验证继续表达不同事实。每条记录突出
当前唯一的下一步；完成后隐藏正常待办操作，异常恢复保留在次级入口。

## 局域网直传的入口到出口

1. 双方打开 RelayPost 并完成本机设置，在附近设备中找到对方，交换公开身份卡并
   各自核验完整安全码。发现广播本身不赋予信任。
2. 发送方选中已核验且可达的设备，选择文件并发送。仍先调用现有 core 产生只供
   目标身份解密的加密包。
3. 接收方先看到发送请求，包含发送身份、文件数量和大小。明确接受后才传输包；
   接收端先校验可信发送者和目标身份，并限制请求和数据体大小。
4. 加密包到达后，接收方明确保存并输入本机密码，由现有 core 解密、校验和提交。
   传输完成不等于文件已保存，未保存不得生成成功回执。
5. 保存成功产生的签名回执自动返回发送方，发送方沿原 core 验证后才显示
   Confirmed。断线重连时可重新取得并验证同一回执，不伪造远端进度，不新增
   第二套持久化状态机。

## 验收要求

- 从无预置收件人的真实首次界面开始，用户能解释对方是谁及如何添加。
- 用户在操作前能解释当前交付方式，以及 Prepare 之后还需要做什么。
- 添加第二个收件人后，返回 Send 明确选中新对象。
- 两个隔离身份以真实网络链路完成发现、双向核验、接收请求、直传、保存和回执；
  拒绝未知或未核验发送者、发给其他身份的包、超限/畸形数据。
- 拒绝接收不写入加密包；接受传输也不自动解密保存。中断后不能误报送达，已保存
  回执可在重新发现后继续完成确认。
- 文件包方式继续从 Send 到最终确认完整走通，复用同一验证与保存权威。
- 在最小窗口和正常窗口检查任务层级、主按钮、状态与完整安全码；工程师操作的
  合成资料验证与独立用户反馈分别记录，不互相替代。

Rust 编译、格式化和测试仅在远端流水线执行。
